# Generate YAK files from Cargo and Go projects

Follows [the plan contract](../../PLANS.md).

## Purpose

A Rust or Go project that builds with `cargo build` or `go build` can be built with yak after one `yak generate`.
Its `Cargo.toml`, `Cargo.lock`, `go.mod`, and `go.sum` stay the source of truth, and the project still builds without yak.
yak builds every dependency that Cargo or Go would build, including third-party crates and modules.

The checked-in output stays small. The repository owner's requirement (2026-09-29) is a few hundred lines at most for a whole project. Reindeer wrote a 12,000-line build file for Roost, a Rust project of the owner's with 6 workspace crates and 775 packages in its `Cargo.lock`. The number of checked-in lines grows with the project's own crates and packages, and never with its third-party dependencies.

To see it working, run `yak generate` in a Cargo workspace and a Go module, count the lines it writes, and run `yak build //...` in each.

## Surprises & Discoveries

- Milestone 1 (2026-09-30): a `YAK` file of five lines builds a crate from its `Cargo.toml`. The project had a workspace `Cargo.toml` with `[workspace.package] edition`, a library crate `util`, and a crate `hello` with a library, a binary, and `util = { path = "../util" }`. Each crate's `YAK` file was:

  ```python
  load(":Cargo.toml", manifest = "value")
  load("//:Cargo.toml", workspace = "value")
  load("//:cargo.bzl", "cargo_package")

  cargo_package(manifest, workspace)
  ```

  `cargo_package` (46 lines) took the name, the edition (inherited through `edition.workspace = true`), and the path dependencies from the manifest, and globbed `src/**/*.rs`. `yak run //hello:hello-bin` and `cargo run -p hello` both printed `HELLO FROM UTIL`. After the dependency on `util` was removed from `hello/Cargo.toml`, the next `yak build //hello:hello-bin` failed with ``error[E0433]: cannot find module or crate `util` in this scope``, and restoring it made the build pass. An edit to `Cargo.toml` reaches the build without regenerating the `YAK` file.
- Milestone 2 (2026-09-30): third-party crates build from `cargo metadata` output with the prelude's rules. The project depended on `serde` with `derive`, `serde_json`, `libc`, and `memchr` under `[target.'cfg(unix)'.dependencies]`, which resolve to 13 packages. A script read `cargo metadata --locked --format-version 1 --filter-platform aarch64-apple-darwin` and the checksums in `Cargo.lock`, and wrote per crate an `http_archive` of `https://static.crates.io/crates/<name>/<name>-<version>.crate`, a `cargo.rust_library` (with `proc_macro` for `serde_derive`), and for crates with a build script a `cargo.rust_binary` and a `buildscript_run`. The library took the build script's results through `env = {"OUT_DIR": "$(location :<id>-build-script-run[out_dir])"}` and `rustc_flags = ["@$(location :<id>-build-script-run[rustc_flags])"]`. `yak run //app:app` printed `{"pid":7,"found":2}`, as `cargo run -p app` did.

Cargo also sets the `CARGO_PKG_VERSION_MAJOR`, `_MINOR`, `_PATCH`, and `_PRE` parts, which the rule can derive from `version`, and package metadata such as `CARGO_PKG_AUTHORS`, which comes from the manifest. The prototype passed them through `env`.

After `memchr` was removed from `app/Cargo.toml` and `Cargo.lock` was regenerated, the next build failed with ``cannot find module or crate `memchr` ``, and restoring both made it pass again. For Roost, `yak targets //...` lists the 26 targets of the 6 members, including the build script targets of `libghostty-vt-sys`.

The member macro now also globs `**/.*` and `**/.*/**`. `include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/../../rscript/tsconfig.json"))` reads a file outside the crate, which Cargo allows and which no glob of the member's package can reach. No proposal yet. Cargo learns such files from rustc's dep-info after a build, and yak needs an action's inputs before it runs.
- Milestone 6 (2026-09-30): with a package per crate, `yak run //app:app` in the project of milestone 2 printed `{"pid":7,"found":2}` again, and the cell copied the 10 packages it read into `yak-out/<isolation dir>/external_cells/cargo/Cargo.toml/`. In Roost, with `DEVELOPER_DIR` naming Xcode, `yak build //... --keep-going` ran 4,642 local actions and copied the 540 packages that the macOS build read. Every target built except `root//crates/roost:roost`, which still fails on its read of `../../rscript/tsconfig.json`.
- `cargo metadata` names a Git package `git+<url>#<version>`, without the commit, and its `source` is `git+<url>#<commit>`. The first version of the cell's directory names hashed only the package ID, so after `cargo update` moved the dependency to a new commit with the same version, the build reused the first commit's copy and printed the old output. The name now hashes the ID and the source.
- `cargo generate-lockfile --offline` refuses to fetch a `file://` Git repository (``can't checkout ... you are in the offline mode``), so the Git test runs Cargo online with a `CARGO_HOME` of its own. Fetching from a local path uses no network.
- With the members in one package and `[package.metadata.yak] include = ["../../rscript/tsconfig.json"]` in `crates/roost/Cargo.toml`, `root//:roost` compiled, and its link failed with `ld: library 'git2' not found`. libgit2-sys's build script found a system libgit2 through pkg-config and printed `cargo:rustc-link-search=native=/opt/homebrew/Cellar/libgit2/1.9.7/lib` and `cargo:rustc-link-lib=git2`. `buildscript_run.py` dropped a search path outside `OUT_DIR`, and rustc records a library's `-l` for the links of its dependents but not its `-L`. Cargo passes the build scripts' search paths to every later rustc run. The runner now keeps such a path and also writes it to a `linker_flags` file, and `buildscript_run` returns a `MergedLinkInfo` whose flags are `@linker_flags`. The generated library of each package with a build script depends on its run target, so the path reaches every link that includes the library. Then `yak build //... --keep-going` built every Roost target (4,643 local actions), `yak generate` wrote 40 lines, and `yak run //:roost` printed Roost's usage.
- `yak test //...` in Roost passed 5 test targets and failed 2. The unit tests of `roost-syntax` look for `examples/libprobe_grammar.dylib` beside Cargo's test binary, and the cell declares no example targets. The unit test of `libghostty-vt-sys` failed with `Library not loaded: @rpath/libghostty-vt.dylib`. Its build script asks for `static=ghostty-vt`, but the `OUT_DIR` directory also holds `libghostty-vt.dylib`, which ld64 prefers for `-lghostty-vt`. `cargo test -p libghostty-vt-sys` links the same dylib (`otool -L`) and passes because Cargo puts the build script's search paths inside `target/` on the dynamic library path of the test.
- The runner now copies the shared libraries of the search paths in `OUT_DIR` into a `shared_libs` output of `buildscript_run`, which also passes `-L<shared_libs>` to the links of dependents. A dependent's link needs the path when the library is dynamic, because rustc bundles only static libraries into the rlib. A test crate with a build script that compiles `libseven.dylib` into `OUT_DIR` showed both failures (`ld: library 'seven' not found` for the dependent binary, then `Library not loaded: @rpath/libseven.dylib` at run time). Setting `DYLD_FALLBACK_LIBRARY_PATH` through an `env` wrapper in `RunInfo` broke every build script run, because `buildscript_run` runs the build script's `RunInfo` as one executable. Each Rust binary instead gets an rpath, relative to itself, to the `shared_libs` directory of each build script among its dependencies, as the prelude does for its shared library symlink tree. Rust libraries pass the directories on through `BuildScriptSharedLibsInfo`. In Roost, `yak test //...` then passed 6 of 7 test targets, including `libghostty-vt-sys-unittest`. The 13 failing tests of `roost-syntax` look for Cargo's example output.
- `cargo metadata` reports one feature set per package (`resolve.nodes[].features`). Cargo's version 2 resolver can build a package with different features for build dependencies and proc macros than for normal dependencies, so this feature set can be a superset of what `cargo build` uses for one of them. The prototype's crates did not exercise the difference.
- A no-op `yak build //...` of the generated Roost took about 4 seconds, and every build printed `File Watcher fresh instance: cleared graph state`. FSEvents flagged `MustScanSubDirs` on the project root with `UserDropped` (flags `0x3`), and `NotifyFileWatcher` then cleared the DICE graph. A cleared graph reruns the write actions and symlink trees of every target, and about 400,000 events under `yak-out` overflowed the stream again, so each build cleared the graph for the next. notify's FSEvents watcher cannot exclude a path, and a watcher that calls `FSEventStreamSetExclusionPaths` on `yak-out` still reported drops. A test that wrote 1.3 million files into an excluded directory received none of their events and 1 to 47 rescans. On a drop, the watcher now compares a crawl of the project's metadata with its previous crawl and invalidates the paths that differ. The crawl of Roost skips `yak-out` and `.git` and covers 181 paths. No-op builds then took 0.04 to 0.05 seconds, with drops still reported.

## Decision Log

- 2026-09-29: The project's `Cargo.toml`, `Cargo.lock`, `go.mod`, and `go.sum` are the source of truth (owner). Autocargo, which Meta released at `github.com/facebookexperimental/autocargo` and archived on 2025-06-05, converts build files to `Cargo.toml`, the opposite direction.
- 2026-09-29: No third-party target is written into the project's repository. A checked-in line per third-party package would already exceed the limit for Roost (775 packages). Third-party targets live in external cells whose build files the daemon creates in memory, as the bundled prelude cell does.
- 2026-09-29: The daemon resolves the dependency graph by running `cargo metadata` and `go list` (owner). Their output matches what `cargo build` and `go build` use, which a reimplementation of Cargo's feature resolution would not guarantee. The Go rules already run the `go` binary. The Rust rules run `rustc`, and a Rust installation through rustup includes `cargo`. The resolution runs on the machine that runs the daemon, so that machine needs `cargo` or `go`, and it may need network access to fetch manifests that are not cached.
- 2026-09-29: Third-party sources download in build actions through `http_archive`, verified by the checksums in `Cargo.lock` and `go.sum`. The daemon only writes the rules. The 2026-09-30 decision on cached sources replaces this one.
- 2026-09-30: The cells serve the third-party sources that `cargo` and `go` downloaded, in place of `http_archive` downloads in build actions (owner). A Go module that `GOPRIVATE` matches skips the module proxy, so no URL exists for a build action to fetch it from, and `go.sum` records `h1:` hashes of the module's files, which no archive digest matches. A private Cargo registry can need a token and source replacement from `.cargo/config.toml`, which `http_archive` cannot apply. `cargo metadata` and `go list -deps` already download every package and check it against `Cargo.lock` and `go.sum`, following the user's configuration and credentials, and they report each package's directory. The daemon copies a package's directory into `yak-out` when a build first reads it and declares it to the materializer, as the `git` origin does with a checkout. Build actions then need no network access, and remote execution receives the sources as source files. The machine that runs the daemon needs network access and the credentials that `cargo build` and `go build` need there.
- 2026-09-30: First-party crates take their targets, dependencies, and features from the `cargo` cell, which writes a `.bzl` file with each workspace member's data from `cargo metadata`. A member's `YAK` file loads the member macro from that file and calls it. Cargo then resolves renamed dependencies, platform-specific dependencies, feature unification, and `workspace = true` inheritance, which a macro reading `Cargo.toml` (milestone 1) would reimplement. Milestone 1 still shows that an edit to a manifest reaches the build, because the cell reads the manifests through DICE.
- 2026-09-30: The cell runs `cargo metadata` once, without `--filter-platform`, and evaluates each dependency's `cfg(...)` or target triple against the cfg values that `rustc --print cfg --target <triple>` reports for each Cargo platform of `prelude/rust/cargo_package.bzl`. A parser in the new crate evaluates `cfg` expressions. The grammar has five productions (`all`, `any`, `not`, a name, and `key = "value"`), and no crate in `Cargo.lock` evaluates them.
- 2026-09-30: The directory of a crates.io package in the cell is `<name>-<version>`, which keeps labels such as `crates//serde-1.0.229:serde` readable. Source replacement keeps a package's crates.io source, and Cargo checks the replacement against the crates.io checksum, so the name identifies the sources. A package from any other source gets an FNV-1a hash of its package ID and source appended, because the copy in `yak-out` is reused by path and the same name and version can have other sources over time.
- 2026-09-30: `yak generate` names the cell `crates` and gives it the path `.crates`. A hidden path cannot collide with a project directory, such as Roost's `crates/`, where a cell path would make the members' packages part of the cell.
- 2026-09-30: For an existing `.yakconfig`, `yak generate` appends `[cells]` and `[external_cells]` sections with the cell. The parser merges a repeated section into the earlier one (`commit_section` in `app/yak_common/src/legacy_configs/parser.rs`), and appending leaves the owner's formatting and comments alone. A new `.yakconfig` lists the cell in the sections that `yak init` writes.
- 2026-09-30: `yak generate` keeps a `YAK` file that differs from the generated one and names it in a warning. `--force` replaces it.
- 2026-09-30: A member's library target is named after the package, or `<package>-lib` when a binary has the package's name. Binaries keep their names, so `yak run //crates/roost:roost` runs the binary. The next decision moves these targets to the workspace's package.
- 2026-09-30: All members' targets are targets of one package at the root of the workspace, whose `YAK` file calls `cargo_workspace()`, in place of a build file per member (owner delegated the choice). A crate that reads files outside its directory, such as Roost's `include_str!` of `../../rscript/tsconfig.json`, names them in `[package.metadata.yak] include` of its `Cargo.toml`, which Cargo ignores. In one package, a glob reaches those files, and the files lie under the members at their paths in the workspace, so `CARGO_MANIFEST_DIR` plus `../..` resolves inside the sources of the action. A package per member keeps labels such as `//crates/roost:roost`, but it would need a build file that exports the listed files and a rule change to place files above a crate's directory. Adding every workspace file outside the members to every crate needs no list, but an edit to any of those files would rebuild every crate. Target names now carry the package name where members could collide: `<package>-unittest`, `<package>-<test>`, and `<package>-<binary>` when two members have binaries of the same name. A duplicate name is an error. The workspace's package also means `yak generate` writes 3 lines of build file in total, and a new member needs no new run.
- 2026-09-30: The cell is configured as `[external_cells] <name> = cargo`, with the workspace manifest's project-relative path in `[external_cell_<name>] manifest`. Its root package holds one target per third-party crate version, named `<name>-<version>`, and an alias `<name>` for each crate that has one version in the graph.

## Context and Orientation

Terms:

- A first-party crate or package is one in the project's own repository. A third-party crate or module comes from a registry, such as crates.io or the Go module proxy.
- An external cell is a cell whose files do not come from the project's repository. `[external_cells]` in the root `.yakconfig` names each one and its origin. `website/docs/users/advanced/external_cells.md` describes them for users.

External cells:

- `app/yak_core/src/cells/external.rs` defines `ExternalCellOrigin`, which has the `Bundled` and `Git` origins.
- `app/yak_common/src/legacy_configs/cells.rs` parses `[external_cells]` and the `[external_cell_<name>]` sections (`parse_external_cell_origin`).
- `app/yak_common/src/external_cells.rs` defines `ExternalCellsImpl`, and `app/yak_common/src/file_ops/delegate.rs` defines `FileOpsDelegate`, the interface through which the interpreter reads a cell's files. `FileOpsKey::compute` in the same file picks the delegate for an external cell.
- `app/yak_external_cells/src/lib.rs` dispatches on the origin. `app/yak_external_cells/src/bundled.rs` serves an in-memory file tree and declares its files to the materializer, which is the model for a generated cell. `app/yak_external_cells/src/git.rs` is the model for an origin that runs an outside program.
- `app/yak_core/src/fs/yak_out_path.rs` (`resolve_external_cell_source`) places an external cell's sources under `yak-out/v2/external_cells/<origin>/`, and each new origin extends its match.

Loading data:

- `load()` of a file whose name ends in `.toml` or `.json` imports its contents as `value` (`app/yak_interpreter/src/load_module.rs`, `website/docs/users/loading_data.md`). The file is read through DICE, so edits to it invalidate the files that load it. `Cargo.toml` can be loaded this way. `go.mod`, `go.sum`, and `Cargo.lock` cannot, because of their extensions.

Prelude rules:

- `prelude/rust/cargo_package.bzl` wraps `rust_library` and `rust_binary` for third-party crates and maps per-platform attributes to `select()`.
- `prelude/rust/cargo_buildscript.bzl` runs a crate's build script (`buildscript_run`) and exposes its `OUT_DIR` and `rustc` flags.
- `prelude/http_archive/http_archive.bzl` downloads and unpacks an archive checked by `sha256`. `.crate` files unpack as `tar.gz`.
- `prelude/go/tools/gopackagesdriver/third-party/YAK` is a hand-written example of third-party Go modules: an `http_archive` of the module zip from `proxy.golang.org` with a sub-target per package directory, and a `go_library` per package.
- `prelude/go/package_builder.bzl` picks the files that match the target platform in the build action, so a Go package's file list does not depend on the platform.

Commands:

- `app/yak/src/lib.rs` registers the subcommands. `app/yak_client/src/commands/init.rs` is a client-side command that writes project files, which `yak generate` can follow.

## Plan of Work

Milestones 1 and 2 are prototypes. Each tests an assumption that later milestones depend on.

1. Prototype: first-party crates from `Cargo.toml`. In a scratch project with one crate, a `YAK` file loads `Cargo.toml` and a macro in a local `.bzl` file declares a `rust_library` and a `rust_binary` from it. Keep the approach if `yak build //...` builds the crate and an edit to `Cargo.toml` changes the next build. Otherwise the generator writes each crate's dependencies into its `YAK` file.
2. Prototype: third-party crates from `cargo metadata`. A script turns the `cargo metadata --locked --format-version 1` output of a small project into `http_archive`, `rust_library`, and `buildscript_run` targets. The project depends on `serde` with `derive` (a proc macro), `libc` (a build script), and one crate with a platform-specific dependency. Keep the approach if `yak build //...` builds and the binary runs. Record which metadata `cargo metadata` lacks, such as the separate host and target features of Cargo's version 2 resolver.
3. The `cargo` origin. `ExternalCellOrigin` in `app/yak_core/src/cells/external.rs` gains a `Cargo` origin that holds the workspace manifest's path, parsed from `[external_cell_<name>] manifest` in `app/yak_common/src/legacy_configs/cells.rs`. A new module `app/yak_external_cells/src/cargo.rs` serves the cell from an in-memory tree, as `bundled.rs` does. A DICE key reads the workspace manifest, `Cargo.lock`, and each member's manifest through DICE, runs `cargo metadata --locked --format-version 1`, and translates the output into the cell's `YAK` file. Parsing the metadata into typed structs, evaluating `cfg` expressions, and writing the file are pure functions with unit tests on recorded `cargo metadata` output. `resolve_external_cell_source` in `app/yak_core/src/fs/yak_out_path.rs` gains the `cargo` arm. `prelude/rust/cargo_buildscript.bzl` derives `CARGO_PKG_VERSION_MAJOR`, `_MINOR`, `_PATCH`, and `_PRE` from `version`.
4. The member macro. The cell also writes `workspace.bzl`, which holds each workspace member's targets (library, binaries, tests, build script), features, and dependencies as `select()`s over the Cargo platforms, and a macro that declares a member's targets from that data. A member's `YAK` file loads the macro and calls it.
5. `yak generate` in `app/yak_client/src/commands/generate.rs`. In a Cargo workspace it writes a `YAK` file per crate, the `[external_cells]` entry, and the `.yakconfig` it needs. It writes a file only when the content differs and leaves hand-written `YAK` files alone unless asked to replace them.
6. Cached Cargo sources. Each third-party package becomes a package of the `cargo` cell, in a directory named `<name>-<version>` that holds the sources from the directory of the package's `manifest_path` and a generated build file. A DICE key per package copies the directory into `yak-out/v2/external_cells/cargo/...` and declares it to the materializer. The cell's root build file keeps the `<name>-<version>` and `<name>` targets as aliases, so labels in `workspace.bzl` do not change. Packages from any registry and from Git build, and a path dependency outside the workspace stays an error, because its sources can change.
7. Go. A `go` origin runs `go list -deps -json` and serves each third-party module from the module cache in the same way, one cell package per Go package. First-party Go packages take their imports from the same `go list` output through a member macro, as Cargo workspace members do.
8. Documentation in `website/docs/` for `yak generate` and the two origins, `ARCHITECTURE.md` for the new crates and origins, and `CHANGELOG.md`.

## Idempotence and Recovery

`yak generate` can run again at any time, and a run with unchanged inputs writes nothing. Generated cells live in memory and under `yak-out/`, so `yak clean` removes them and the next command recreates them.
