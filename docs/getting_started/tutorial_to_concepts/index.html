From Tutorial to Concepts

In the previous tutorials, we’ve created YAK files, defined a couple of targets and successfully built and ran the “Hello World” rust binary and even wrote and ran a test. Great job done! Now, let’s go through the journey again, weaving in the core concepts as we go along to see what gets involved during this learning process.

Understanding Target Labels​

This is one of the most important concepts to understand when using yak. It is a precise way to identify any buildable unit in your codebase.

In the tutorials, you encountered the following target label like root//yak_lab/greeter_bin:main.

Here is the anatomy of a target label:

root
Cell Name
//
yak_lab/greeter_bin
Target Package
:
main
Target Name

Cell​

Cell defines a directory tree of one or more yak packages. The root of a yak cell contains a global configuration file called .yakconfig.

You can run yak audit cell to inspect the abs path of each cell root.

Package​

The existence of a YAK file (yak_lab/greeter_bin/YAK) makes yak_lab/greeter_bin a yak package, which is more than a directory. If a yak target uses the source file as input, that target is regarded as the owner of the source.

Target name​

The name of the target in the package. It is the name we defined in the YAK file.

rust_binary(
    name = "main",
    srcs = ["main.rs"],
    ...
)

It should be unique within the package.

YAK file​

In the lab, you’ve already created three build files:

  • greeter_bin/YAK
  • greeter_lib/YAK
  • logging_lib/YAK

Although configurable, the name of the build file normally is just YAK.

In these YAK files, you’ve written a couple of yak targets, :main, :library, :logging_lib and :test. yak targets are instances of build rules, which defines how the target should be built. For example, target :main is of rule type rust_binary, the output artifact will be a binary that’s runnable, while :library, :logging_lib are of rule type rust_library, the output of which will be a library that can be linked to the binary.

Referring to yak targets in YAK files and CLI commands need to follow a special target pattern, which looks like:

cell//path/to/dir:target or cell//path/to/dir/...

you will soon become very familiar with these patterns during daily development.

Tips:​

  • yak targets can be either build rules or macros, which are wrappers/extensions around native build rules, macros are usually defined .bzl files.
  • yak uses starlark language which is a dialect of python, to define build rules and macros.

Load Function and Attributes​

A YAK file can start with one or more load functions, which load macros from .bzl files for this YAK file to use, this is similar to load or include functions in other programming languages, load function takes the following syntax: load("@cell//path/to/bzl:some_bzl.bzl", "some_macro")

Each yak target has a set of attributes, which provide powerful ways to define and customize how the build should be done, you can inspect the rule definition to see what these attributes are and the syntax to define them. Some attributes are mandatory and some are optional with defaults. Most attributes are rule-specific but there are common ones such as name, srcs, deps and visibility.

Tips:​

  • Without using load function, yak will default to using native rules with the same name;
  • One load function can load multiple macros from the same .bzl file
  • Deps and visibility are important attributes to understand, please read the docs!

Dependencies and Dependency Graph​

As you craft your program, you may need to rely on other targets, known as dependencies. In the "Hello World" exercise, :library and :logging_lib targets are dependencies of the :main target. One target can depend on multiple dependencies, which in turn can have their own dependencies to form a web of connections, a so-called dependency graph, our lab renders a very simple dependency graph with maximum depth of 2, in real world, the graph will be much bigger and one top level target could have tens of thousands dependencies.

Understanding and managing the dependency graph of your yak target is important for effective development. yak also offers powerful query tools to explore the dependency graph.

Tips:​

  • Dependency graph size affects build speed and memory usage greatly
  • The graph is a DAG graph. So cycles in the dependency graph (circular dependency), something like A->B->...->X->A, are not allowed, yak will emit error when cycle is detected.

yak commands​

In the lab, once yak and source files are in place, we use yak build :main --show-output to build the :main target. This uses the yak build command to compile and link your rust code into a binary. Now let’s take a closer look at this command. A yak command is usually composed of a command type ( build, run, test ...), some target pattern, and options. Command options can offer extra configurations to do the build.

yak accepts multiple targets in one command, such as:

  • yak build target1 target2 target3 builds 3 targets in one command

  • yak build //path/to/dir/... builds all targets under path/to/dir, including sub-dir

  • yak build //path/to/dir: build all targets under package path/to/dir, without sub packages

  • yak build @a-file builds targets listed in a-file, which is a plain text file

yak builds multiple targets in parallel, unless there are dependencies between them.

Once target is built, you can use yak run, yak test and yak install to test the code.

As you become more adept, you can explore other powerful yak commands, such as:

  • yak query with various options to analyze the dependency graph, this set of commands is by far the most powerful and complicated yak commands to use;
  • yak kill to stop running yak daemon, this is sometimes needed to recover from a failed build due to bad daemon state;
  • yak clean to remove build artifacts from yak-out, this is a remedy to recover from failed build due to either bad daemon or bad artifacts in cache;
  • yak log to see information about previous builds
  • yak bxl to run bxl scripts. BXL is a yak script language using starlark syntax to write complex query or build logic.

Tips:​

  • yak offers help menus for all commands, try the -h option, you can yak -h or yak build -h to see all available commands and options

Console and Output​

During the lab, you’ve seen the console output during build and test process, these outputs give information about the execution progress and state. yak offers different kinds of consoles for various purposes, and the interactive feature helps during debugging.

yak-out​

So you’ve successfully built the target and run it. Finally, let’s briefly talk about yak-out, which is an important concept yet hard to understand initially. We know that yak builds complicated targets with big dependency graphs and generates tons of outputs for test and run. Where should these output artifacts be stored at? The outputs should not be stored at the source directory which is tracked by the source control system. The outputs also need to be reused/cached for later builds to save build time. So here comes yak-out,it has the following characteristics:

  • It’s under repo root;
  • It has a unique file structure, some directories are hashed for caching purpose;
  • It stores a lot of data including output artifacts, yak log files, tmp data, etc;
  • It is managed by yak and developers normally should not manipulate;

Tips:​

  • Do NOT delete artifacts manually from yak-out directory and expect yak to rebuild them, yak doesn’t track things under yak-out, use yak clean instead;
